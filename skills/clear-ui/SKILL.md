# Clear UI

降低寻找、辨认、理解、操作和恢复的总成本。视觉分区也是信息：密集内容必须能识别归属，输入控件必须能在默认态被认出。常见状态优先用固定语义图标，必要时才补可见文字，始终保留可访问名称与解释途径。简约不以元素少、点击少、颜色少或字体小来证明。

## 使用

1. 从用户任务和真实画面识别主要阻碍。先说明用户需要判断什么、操作哪个对象；保留已经确认的产品模型与设计方向。
2. 读取[规则与实践索引](references/index.md)，只加载适用条目。`references/rules` 是带正向要求、禁止项和验证方式的原子规则；`references/patterns` 是组件作用、适用场景、取舍与反例。不要一次加载全部条目，也不把指南当作必须堆上的组件清单。
3. 用“问题证据 → 规则ID → 布局/组件选择 → 预期收益”给出精简方案。选择组件时说明为什么适合、什么情况下改用别的模式；不把卡片或抽屉当万能容器。
4. 用户要讨论就交付判断；用户要改界面就沿项目技术栈和授权实现。与已有视觉设计Skill配合时，本Skill负责信息与交互取舍，不另建第二套视觉体系或强制重设计。
5. 验证受影响的真实任务、截图和关键状态。区分“观察到的问题已修复”“操作实测通过”“用户验证通过”；无障碍扫描、截图整洁和主观评分都不能替代完整任务验证。不要求达到虚假的满分。

命中适用条件的规则必须检查；不通过时留下具体finding并修正，用户明确选择例外时记录取舍。不要用“极简风格”豁免无法识别的分区和控件，不将主观审美伪装成机器可证明的通过项。

## 模块

| 命名空间 | 回答的问题 |
| --- | --- |
| `ui.clarity.*` | 信息为什么难理解、难定位，怎样减少认知工作 |
| `ui.pattern.*` | 哪种组件或布局适合当前任务，边界在哪里 |
| `ui.behavior.*` | 状态、操作、失败恢复和不同设备上是否清晰可靠 |
| `ui.visual.*` | 区域边界和表面强调是否足以表达归属与层级 |
| `ui.controls.*` | 输入控件是否无需试探即可识别和使用 |

每项一个文件，文件名等于ID。修改时维护原ID；新增项需要独立判断价值，优先修订原规则。规则与指南都为持续复核的规范，硬性要求针对可观察的识别与使用问题，不规定所有页面必须使用某种风格；反例是维护合同的一部分。

## 评审输出

按影响排序列出少量发现：具体画面/任务证据、规则ID、改法、验证结果；未适用标N/A并说明原因。无需为每条规则写一份重复报告。没有实测的数据不能给“寻找时间降低了多少”等量化结论。

[来源与推导边界](references/sources.md)区分外部规范、常见模式与本Skill的实践判断。维护后运行 `python3 scripts/validate.py` 检查ID、索引和本地链接；它不证明设计质量。
